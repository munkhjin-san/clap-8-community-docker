# 「アプリ」機能（内部名: Flow）クライアント向け分析

分析日: 2026-07-17  
対象: `/apps` に実装された最新のカスタム業務アプリ機能

## 1. 結論

「アプリ」は、会社ごとの業務をノーコードに近い操作でデジタル化する、MISO内蔵の業務アプリ基盤です。

単なる申請・承認フォームではありません。管理者が「入力フォーム」「データ一覧」「処理ステータス」「権限」「帳票」を組み合わせて業務アプリを作り、利用者が同じ画面から登録、検索、処理、共同作業、証跡確認まで行えます。

クライアント向けの最も短い説明は次のとおりです。

> Excel、紙、メール、個別SaaSに散らばった社内業務を、MISOの中に自社専用アプリとして作り、データと業務フローを一体で運用できます。

### 製品名と内部名

- 利用者向け名称: **アプリ**
- URL: `/apps`
- コード・データモデル上の内部名: **Flow**
- プレゼンテーションでは「Flow」ではなく「アプリ」を主名称にする
- 「Flow」は、アプリの中で処理の状態を動かすワークフローエンジンとして説明すると分かりやすい

## 2. 解決する課題

従来の社内業務では、入力はExcel、申請はメール、承認状況はチャット、証跡は別フォルダという分断が起きやすくなります。「アプリ」は次の要素を一つの業務単位にまとめます。

- 業務に合わせた入力フォーム
- 一覧、検索、フィルター、並び替え
- ステータスと処理ボタン
- 担当者ごとの対応待ち
- コメントと変更履歴
- 閲覧・編集・管理権限
- CSV入出力
- PDF帳票
- 監査ログ

そのため、経費・仮払、顧客台帳、送付依頼、予算管理など、異なる業務を同じ操作体系で運用できます。

## 3. 全体コンセプト

```mermaid
flowchart LR
    A["管理者が業務アプリを設計"] --> B["フォーム・計算・一覧を設定"]
    B --> C["ステータスと処理ボタンを設定"]
    C --> D["利用者・役職・プロジェクト別に権限設定"]
    D --> E["利用者がレコードを登録"]
    E --> F["担当者の『対応待ち』に表示"]
    F --> G["確認・承認・差し戻し等の処理"]
    G --> H["コメント・変更履歴・監査ログを保存"]
    H --> I["CSVやPDFで既存業務とも連携"]
```

システムは二つの層でできています。

1. **アプリ定義**: フォーム、ビュー、ステータス、権限、ツールをまとめた再利用可能な業務設計
2. **レコード**: そのアプリに登録され、現在のステータスや値、コメント、履歴を持つ一件の業務データ

この「設計」と「実データ」の分離により、一度作った業務ルールを繰り返し利用できます。

## 4. 利用者の体験

### 4.1 アプリポータル

利用者はサイドメニューの「アプリ」からポータルを開きます。

ポータルでは次の操作ができます。

- 利用可能なアプリをカードまたはリストで表示
- アプリ名で検索
- 新しい順、古い順、更新順、名前順、自分が作成したアプリで並び替え
- よく使うアプリをピン留め
- アプリごとのレコード件数と項目数を確認
- 自分が処理できるレコードだけを「対応待ち」で横断表示

ライブ環境では、予算管理、仮払管理、送付状、取引先マスタなど複数用途が同じポータルに並び、取引先マスタは101件、個人の対応待ちは28件でした。これは「承認機能」よりも「共通業務基盤」として見せる方が実態に合うことを示します。

### 4.2 レコード一覧

アプリを開くと、登録されたレコードが表形式で表示されます。

- アプリ別の連番ID
- 現在のステータス
- 業務項目と計算結果
- 作成日時・更新日時
- キーワード検索
- 複数条件の一時フィルター（AND / OR）
- 管理者が作成した保存済みビュー
- 列の並び、フィルター、並び替え
- 行からの詳細表示、編集、削除
- 権限がある場合の一括削除
- CSV取込・出力

保存済みビューを使えば、同じデータから「未処理」「自分の担当」「今月分」など、目的別の一覧を用意できます。

### 4.3 レコード詳細

一件のレコード画面には次が統合されています。

- 業務フォームの値
- 現在のステータス
- 実行可能な次のアクションボタン
- 編集・削除
- PDF帳票の出力ボタン
- コメントとメンション
- 添付ファイル
- 項目変更とステータス変更の履歴

ライブ確認した仮払管理では、「未処理」から「管理者へ申請する」という次の操作が画面上部に明示されていました。利用者は業務フロー図を覚えなくても、その時点で可能な操作をボタンとして選べます。

### 4.4 対応待ち

「対応待ち」は、アプリを横断して、現在の利用者が押せるアクションを持つレコードを集約します。

各行にはアプリ名、レコード番号、現在のステータスが表示され、対象レコードへ直接移動できます。これにより、利用者は個別アプリを巡回して処理待ちを探す必要がありません。

## 5. アプリ作成者の体験

アプリ設定は、次の7タブで構成されています。

### 5.1 基本情報

- アプリ名とリッチテキスト説明
- 有効 / 停止中
- 画像アップロードによるアイコン
- AIによるアイコン生成
- 12色のテーマカラー
- 全レコード削除と採番リセット（専用権限が必要）

### 5.2 フォーム

ドラッグ＆ドロップまたはクリックで項目を追加し、横並びや幅を調整できます。

利用可能な項目は次の21種類です。

- 入力: 短文、長文、数値、日付、時刻、日時
- 選択: ドロップダウン、ラジオ、チェックボックス、オン/オフ
- 高度: ユーザー、メンバー、計算、ルックアップ、プロジェクト
- その他: ファイル、テーブル
- レイアウト: 見出し、ラベル、スペース、罫線

主な高度機能:

- 必須、文字数、数値範囲、形式、選択数、日付範囲、ファイル形式・サイズなどの入力ルール
- 新規作成時の初期値、現在日時、作成者
- 入力禁止にしてルックアップだけで自動入力する項目
- 明細行を持つテーブル
- テーブル内の計算列・ルックアップ列
- 他アプリのレコードを参照するルックアップ
- 参照元の項目を現在のアプリにコピーするフィールドマッピング
- フィールドや明細列を参照する計算式

計算式はIF、SUM、MIN、MAX、ROUND、CONTAINS、AND、ORなどに対応し、テーブル列の集計や計算項目同士の連鎖もできます。

### 5.3 フロー設定

ステータス機能はアプリごとにオン・オフできます。

- オフ: 通常のデータベース / 台帳アプリ
- オン: レコードにステータスと処理ボタンを追加した業務フローアプリ

設定画面ではステータスをブロックとして配置し、各ステータスから実行できるアクションボタンと遷移先を設定します。アクションの実行者は、作成者、個別ユーザー、役職、作成者に関係するプロジェクトPM、レコードで選択されたプロジェクトのPMなどから指定できます。

各ステータスでは、項目ごとに次を設定できます。

- 編集可
- 閲覧のみ
- 非表示

重要: 初期設計資料では直線的な承認と一段階の差し戻しを想定していましたが、現行実装は任意の遷移先を持つアクションボタン方式です。クライアントには「直線的な承認フロー」ではなく「業務に合わせたステータス遷移」と説明するのが正確です。

### 5.4 ビュー

アプリ作成者は複数の一覧表示を作成できます。

- ビュー名
- 既定ビュー
- 表示列と順序
- 複数フィルター（保存済みビューは全条件一致）
- 複数の並び替え条件

ID、ステータス、作成日時、更新日時などのシステム項目も列として利用できます。

### 5.5 ツール

現在のツールはPDF帳票です。

- A4縦 / 横
- テキスト、項目、当日、画像、枠、線、明細テーブルを配置
- フォント、色、罫線、配置、数値・日付形式を設定
- 明細の小計、税、合計、通貨、ヘッダー、罫線を設定
- レコード画面からPDFを生成

見積書、請求書、申請書、送付状など、登録済みデータを再入力せず帳票化できます。

### 5.6 アクセス権

アクセス制御は三層です。

1. **アプリ権限**: 閲覧、追加、編集、削除、管理、CSV取込、CSV書出、一括処理
2. **レコード権限**: 作成者、更新者、ステータス、項目値などの条件に合うレコードを誰が閲覧・編集・削除できるか
3. **フィールド権限**: 項目単位で誰が閲覧・編集できるか

対象は、全員、個別ユーザー、役職、プロジェクトメンバー、PM、ディレクターなどです。アプリ権限は上から順に評価し、最初に一致した設定が採用されます。レコード権限はアプリ権限の範囲を超えず、フィールド権限とステータス別ルールも同時に適用されます。

### 5.7 監査ログ

アプリ全体の監査ログでは次を記録します。

- レコード閲覧
- CSV出力
- 設定変更
- ファイルダウンロード

設定変更では、基本情報、フォーム、フロー、権限、ビュー、ツールの差分を確認できます。CSV出力では、ファイル名、出力範囲、文字コード、行数を記録し、その出力ファイルを再ダウンロードできます。

これはレコード内の「変更履歴」と別です。

- 変更履歴: 一件のレコードの項目変更・ステータス変更
- 監査ログ: アプリ全体の閲覧・出力・設定操作

## 6. データ連携と既存資産の活用

### kintone取込

新規アプリ作成時にkintoneの定義を読み込み、項目、計算式、テーブル、ステータス、アクションをアプリ設定へ変換できます。担当者設定は自動移行対象外で、取込後に確認・設定する前提です。

### CSV

- UTF-8 / Shift-JISで出力
- 全項目または指定テーブルだけを出力
- 作成日時・更新日時を含められる
- CSV列を既存項目へ割り当て
- 未定義列から新規項目を作成
- 明細行のCSVを既存または新規テーブルへ取り込む
- 取込元と外部IDを記録して更新に利用

### アプリ間連携

ルックアップで別アプリのレコードを検索・選択し、必要な項目を現在のレコードへコピーできます。コピー値はスナップショットなので、後から参照元が変わっても自動上書きされません。コピー先は通常項目として検索、フィルター、一覧、CSV出力に利用できます。

## 7. クライアント価値

### 業務部門

- 自分たちの業務に合わせた画面と処理手順
- 対応待ちを一か所で確認
- コメントと履歴を業務データに集約
- Excelの最新版問題やメール承認の見落としを削減

### 管理者

- 開発プロジェクトを立ち上げずに業務アプリを構成
- 役職・プロジェクト・データ条件に合わせた権限
- フォーム、一覧、フローを継続的に改善
- 監査ログで閲覧・出力・設定変更を追跡

### 経営・IT

- 個別ツールの乱立を抑え、MISOに集約
- 共通認証、ユーザー、役職、プロジェクト情報を再利用
- kintoneやCSVから段階的に移行
- 既存のMISO機能と同じ画面・ナビゲーションで運用

## 9. 5分デモの推奨シナリオ

1. `/apps` を開き、複数の業務アプリと検索・ピン留めを見せる
2. 「対応待ち」を開き、アプリ横断の自分のタスクを見せる
3. 仮払管理のレコードを開き、現在ステータスと「管理者へ申請する」を見せる
4. コメントと変更履歴を見せる
5. アプリ設定のフォームを開き、項目・テーブル・計算式を見せる
6. フロー設定のビジュアルなステータス図を見せる
7. アクセス権と監査ログを見せて締める

デモでは実データに対する「保存」「削除」「ステータス実行」を行わず、必要なら事前に専用デモアプリとデモレコードを作成します。

## 10. 現時点の完成度と注意点

### プレゼンテーションで強く訴求できる点

- ポータル、一覧、詳細、ビルダーまで一貫した実画面が存在する
- 台帳型とワークフロー型の両方に対応する
- フォーム、計算、明細、ルックアップが実業務レベル
- 「対応待ち」がアプリ横断の行動導線になる
- 三層権限と二種類の履歴で管理・監査の説明ができる
- kintone、CSV、PDFが導入・移行の障壁を下げる
- モバイル向けに詳細画面の操作が統合されている

### デモ前に整えるべき点

- **既定ビューの列数**: ライブの仮払管理は32列が既定表示され、横スクロールが非常に長い。デモ用に主要列だけのビューを作る
- **サンプルデータ**: 空欄が多いテストレコードでは価値が伝わりにくい。正常な申請一件を用意する
- **ステータス文言**: 長いステータス・ボタン名は図で省略表示されるため、短い業務用語に整える
- **権限説明**: first-match-winsと三層の交差は強力だが複雑。クライアント説明では図を使う
- **用語統一**: 外向けは「アプリ」、技術説明だけ「Flowエンジン」を使用する
- **個人情報**: 現在のデータには氏名、口座等の業務情報が含まれる。クライアント向け画面収録は匿名データで行う

### 品質・技術上の注意

- Flow専用の自動テストは現時点で計算エンジン中心。2026-07-17時点で66テスト・139アサーションは成功した
- CRUD、権限、ステータス遷移、CSV、PDF、監査ログの専用統合テストは確認できない
- レコード権限を使うアプリ、または計算項目で絞込・並替する一覧は、全件取得後にクライアント側処理へ切り替わるため、大量データで性能検証が必要
- アプリ権限は上から最初に一致した行が優先されるため、設定順序の誤りを防ぐ運用ガイドが必要
- 旧 `docs/approval-flow-design.md` は実装前の設計であり、現在の任意アクション遷移、ビュー、三層権限、PDF、監査ログなどを反映していない

## 11. 避けるべき表現

現時点の実装確認だけでは、次の断定は避けます。

- 「完全ノーコード」: 高度な計算式、権限設計、移行設定には管理者知識が必要
- 「すべての承認を自動化」: 通知、期限、代理承認、条件分岐の全仕様は今回確認範囲にない
- 「大規模データでも無制限」: 一部条件ではクライアント側全件処理になる
- 「kintoneを完全自動移行」: 担当者設定などは取込後の調整が必要
- 「監査ログがすべての操作を記録」: 監査対象は現在、閲覧、CSV出力、設定変更、ファイルダウンロード。レコード編集は別の変更履歴で管理
